# 자동차 경주

### 기능 요구 사항(정리)
초간단 자동차 경주 게임을 구현한다.
- 자동차 이름을 입력받는다.
  - 이름은 쉼표(,)로 구분하며, 이름의 길이는 5자 이하로 제한한다.
- 몇번을 시도할건지 입력한다.
- 자동차(들)는 전진하거나 정지한다.
  - 0 ~ 9까지의 난수 중 4 이상일 경우에만 전진한다. ("-" 추가함으로써 전진 판단)
  - 매 시도마다 각 자동차의 진행 상태를 출력한다.
- 우승자를 선정한다.
  - 우승자가 2명 이상일 경우, 쉼표(,)로 구분한다.
- 사용자가 잘못된 값을 입력할 경우 IllegalArgumentException을 발생시킨다.

### 입출력 요구 사항
입력
- 경주할 자동차 이름(이름은 쉼표(,) 기준으로 구분)
```
pobi,woni,jun
```
- 시도할 횟수
```
5
```

출력
- 차수별 실행 결과
```
pobi : --
woni : ----
jun : ---
```
- 단독 우승자 안내 문구
```
최종 우승자 : pobi
```

- 공동 우승자 안내 문구
```
최종 우승자 : pobi, jun
```
실행 결과 예시
```
경주할 자동차 이름을 입력하세요.(이름은 쉼표(,) 기준으로 구분)
pobi,woni,jun
시도할 횟수는 몇 회인가요?
5

실행 결과
pobi : -
woni : 
jun : -

pobi : --
woni : -
jun : --

pobi : ---
woni : --
jun : ---

pobi : ----
woni : ---
jun : ----

pobi : -----
woni : ----
jun : -----

최종 우승자 : pobi, jun
```

### 추가된 프로그래밍 요구 사항
- depth는 2까지만 허용한다.
- 함수나 메서드는 한 가지 일만 담당하도록 최대한 작게 설계한다.
- 3항 연산자는 허용되지 않는다.
- 테스트 도구로 프로그램이 정상적으로 동작하는지 확인한다.

### 구현할 기능(정리)
이번 과제에서도 MVC 패턴을 적용할 예정이다. 1주차에서 회고했던 내용을 참고해서 모델을 세부적으로 분리하고, 추상화 전략을 도입해볼 생각이다. 
- `Model(Car)`: 전진 혹은 정지하는 책임을 맡는다.
- [x] 자동차는 이동 전략을 주입 받아 기준에 부합하면 자동차를 전진시킨다. (`move()` 메서드)
- [x] 자동차는 이름에 공백이 입력될 경우, IllegalStateException 예외를 발생시킨다.
- [x] 자동차는 이름이 5자를 초과할 경우, IllegalStateException 예외를 발생시킨다.
- [x] 자동차는 이름에 특수문자가 포함되어 있을 경우, IllegalStateException 예외를 발생시킨다.

&nbsp;

- `Model(MoveStrategy)`: 특정 조건에 따라 자동차의 전진 혹은 정지 여부를 판단하는 책임을 맡는다. 향후 다양한 이동 전략이 추가될 수도 있기 때문에 인터페이스로 추상화하는 것이 적절하다고 생각했다.
- [x] 자동차 전진 조건 정의(MoveStrategy 인터페이스)
- [x] 현재 과제에서 주어진 조건 0 ~ 9까지의 난수 중 4 이상이 나올 경우에만 전진하는 구현체를 구현한다. (`BasicMoveStrategy` 구현체)
  - [x] 기준값(요구 사항에서는 4) 이상의 수가 나올 경우, 전진 여부로 true를 반환한다.
     
&nbsp;
     
- `Model(NumberGenerator)`: 요구 사항에 맞는 범위 안에서 난수를 생성하는 책임을 맡는다.
- [x] camp.nextstep.edu.missionutils에서 제공하는 Randoms API를 사용해서 난수를 생성한다. 

&nbsp;

- `Model(Winner)`: 최종 우승자를 선정하는 책임을 맡는다.
- [x] 각 자동차들이 가진 전진 위치들 중 최댓값을 찾는다. (`findLargestPosition()` 메서드)
- [x] 어떤 자동차도 전진하지 않았을 경우, 우승자를 선정할 수 없다는 규칙을 추가하면서 IllegalStateException 예외를 발생시키도록 처리한다. (`validateAllCarsMoved()` 메서드)
- [x] 가장 큰 전진 위치값과 같은 위치값을 가지고 있는 자동차들을 반환한다.(`getWinners()` 메서드)

&nbsp;

- `Service(GameService)`: 입력된 자동차들의 이름을 파싱 및 검증과 입력된 시도 횟수에 대한 검증을 수행하고, 검증이 완료된 데이터들을 바탕으로 자동차들이 들어 있는 목록을 반환하는 책임을 맡는다.
- [x] 입력받은 자동차 이름들을 쉼표를 기준으로 파싱한다. (`parseCarNames()` 메서드)
- [x] 입력받은 자동차 이륻들 중 중복된 이름이 있는지 검증한다. (`validateDuplicateCarName()` 메서드)
- [x] 입력받은 시도 횟수가 숫자인지 검증한다. (`validateRoundIsInteger()` 메서드)
- [x] 입력받은 시도 횟수가 양수인지 검증한다. (`validateRoundIsPositive()` 메서드)
- [x] 검증이 완료된 자동차 이름(들)을 바탕으로 자동차 인스턴스(들)가 담긴 리스트를 반환한다. (`initCarList()` 메서드)

&nbsp;

- `View(InputView)`: 자동차의 이름과 시도 횟수를 사용자로부터 입력받는 책임을 맡는다.
- [x] 자동차 이름을 입력 받는다. (`inputCarNames()` 메서드)
- [x] 시도할 횟수를 입력 받는다. (`inputRounds()` 메서드)

&nbsp;

- `View(OutputView)`: 시도 횟수마다 진행 상태를 출력하고, 우승자를 출력하는 책임을 맡는다.
- [x] 자동차 진행 상태를 출력한다. (`printProgress()` 메서드)
- [x] 우승자를 출력한다. (`printWinners()` 메서드)

&nbsp;

- `Controller(GameController)`: `View`로부터 입력받은 데이터를 각 `Model`들과 `Service`로 전달 후 결과를 반환받는다. 반환받은 결과를 `OutputView`로 전달하는 책임을 맡는다.
- [x] 자동차 이름을 `InputView`로부터 입력 받는다.
- [x] 시도할 횟수를 `InputView`로부터 입력 받는다.
- [x] `GameService`로 입력된 자동차 이름 문자열을 전달하고, 최종 Car 리스트를 반환받는다.
- [x] 시도 횟수동안 반환받은 진행 상태를 `OutputView`로 전달하고, 진행 상태를 출력한다.
- [x] 반환받은 우승자(들)를 `OutputView`로 전달하고, 최종 우승자(들)를 출력한다.

&nbsp;

-`Test(CarTest)`: 자동차가 가질 수 있는 이름에 대해 발생할 수 있는 예외들에 대한 테스트를 수행한다.
- [x] 자동차의 이름에 아무 입력이 들어오지 않은 경우, IllegalArgumentException 예외에 대한 테스트 코드 작성(`이름_공백_제한()`)
- [x] 자동차의 이름이 5자를 초과할 경우, IllegalArgumentException 예외에 대한 테스트 코드 작성(`이름_길이_제한()`)
- [x] 자동차의 이름에 특수 문자가 포함되어 있을 경우, IllegalArgumentException 예외에 대한 테스트 코드 작성(`이름_특수문자_허용_불가()`)

&nbsp;

- `Test(WinnerTest)`: 우승자를 선정할 때, 최소 1대 이상은 전진해야 우승자를 선정할 수 있다는 가정 하에 단독 우승자, 공동 우승자를 선정하는 테스트를 수행한다.
- [x] 게임에 참가하는 모든 자동차들이 한 번도 전진하지 않았을 경우, 우승자를 선정할 수 없다는 IllegalStateException 예외에 대한 테스트 코드를 작성(`우승자_없음()`)
- [x] 우승자가 1대일 경우, 우승자 리스트에 정확히 그 우승한 자동차 이름만 포함되어 있는지에 대한 테스트 코드 작성(`단일_우승()`)
- [x] 우승자가 여러 대일 경우, 우승자 리스트에 우승한 자동차 이름들이 포함되어 있는지에 대한 테스트 코드 작성(`공동_우승()`)

&nbsp;

-`Test(NumberGeneratorTest`): 난수 생성기에 대한 기본적인 단위 테스트를 수행한다.
- [x] 주어진 범위 내에서 임의의 숫자가 생성되는지 검증(`범위_내_숫자_생성()`)
- [x] 잘못된 범위가 주어질 경우, IllegalStateException 예외에 대한 테스트 코드를 작성(`잘못된_범위_예외()`)

&nbsp;

-`Test(BasicMoveStrategyTest)`: 이동 전략이 가질 수 있는 예외들에 대한 테스트를 수행한다.
- [x] 뽑힌 임의의 난수가 기준값 미만이면 정지하는지 검증(`기준값_미만_전진_불가()`)
- [x] 뽑힌 임의의 난수가 기준값 이상이면 전진하는지 검증(`기준값_이상_전진()`)

&nbsp;

- `Test(GameServiceTest)`: 자동차(들)가 담긴 리스트를 초기화 할 때, 발생할 수 있는 예외들에 대한 테스트를 수행한다.
- [x] 자동차의 이름이 5자를 초과할 경우, IllegalArgumentException 예외에 대한 테스트 코드 작성(`이름_5자_초과()`)
- [x] 자동차의 이름에 아무 입력이 들어오지 않은 경우, IllegalArgumentException 예외에 대한 테스트 코드 작성(`이름_입력없음()`)

### 고민한 부분
- `내용`: Car 모델에 이동 전략 코드가 존재해도 되는지에 대한 고민을 했다. 왜냐하면 MVC 패턴을 학습할 때, 모델은 본인의 데이터만 관리해야 하는 것으로 이해했기 때문이다.
- `해결 방법`: `MoveStrategy` 인터페이스에만 의존하도록 처리함으로써 최대한 Car 모델 본인의 데이터를 관리하고 책임을 맡도록 했다. 따라서 DIP 원칙에도 위배되지 않기 때문에 MVC 패턴에도 전혀 어긋나지 않다고 판단했다.

&nbsp;

- `내용`: 기존 구현할 기능을 정리한 부분에서 향후 정지 시에는 'X' 문자가 추가되는 등 특정 처리가 있을 수 있다는 생각에 전진 기능만으로 조건문을 사용해 정지 여부도 동시에 처리하는 것보다 정지하는 것도 명확하게 기능이 있다는 것을 알아볼 수 있도록 정지 기능도 정의해주려고 했는데, 인터페이스와 구현체를 구현하다보니 굳이 정지 기능도 정의해야 하는지 의문이 들었다.
- `해결 방법`: 정지 기능을 정의하지 않고, 불리언 타입으로 반환되는 `move()` 메서드를 가지고 조건문을 통해 충분히 정지일 경우에도 로직을 추가할 수 있다고 생각했다. 따라서 인터페이스에도 전진하는 행동만 정의하고, 정지하는 행동은 따로 정의해주지 않았다. 인터페이스는 작을수록 교체와 테스트가 쉽고, 과한 추상화는 오히려 제약이 될 수 있다는 생각을 했다.

&nbsp;

- `내용`: 이동 전략 로직에 공통 상수를 설정해도 되는지 고민을 했다. 예를 들어, `MIN_NUMBER`, `MAX_NUMBER`와 같은 상수는 이동 전략이 아닌 숫자 생성기(`NumberGenerator`)로 옮기는 것이 더 적절한지, 혹은 따로 공통 상수를 관리하는 클래스를 별도로 만들어야 하는 것인지를 생각했다.
- `해결 방법`: 기존에는 `NumberGenerator`에 공통 상수를 import해서 사용했지만, 오로지 이동 전략이 규칙(공통 상수)을 가지고, 숫자 생성기는 그 규칙에 맞게 난수를 생성하도록 이동 전략으로부터 인자를 받게 리팩토링했다. 추가로 오로지 이동 전략만이 규칙을 가지고 있고, 다른 외부 클래스에서 규칙에 접근할 필요가 없기 때문에 더 이상 공통 상수가 아닌 이동 전략만의 데이터로 제한해줬다.

### 아쉬운 점
설계를 마치고 다시 전체 프로그램을 살펴보니, `Car`에 대한 이름과 전진 위치와 같은 데이터를 `Map` 자료구조를 이용해서 처리했다면 더 깔끔해지지 않았을까 하는 아쉬움이 남았다. 

추가로, 예외 처리에 대한 검증 로직을 메서드로 일일이 쪼개서 해당 클래스의 생성자에서 검증을 수행하도록 했는데, 검증 로직이 많아질수록 생성자의 코드가 길어져서 가독성도 떨어지는 문제를 인식했다. 다음 과제부터는 생성자를 `private`으로 제한하고, 정적 팩토리 메서드를 도입해서 검증 로직을 더 깔끔하게 가져가고 인스턴스를 생성해야겠다는 생각을 했다. 

추가로 테스트 코드를 작성할 때도 굉장한 어려움이 있었다. 어떤 테스트를 작성해야 할지도 문제였지만, 테스트를 먼저 작성하고 로직을 구현해야 하는지, 아니면 로직을 모두 구현하고 테스트를 수행해야 하는지, 틈틈이 테스트를 수행해야 하는지 의문이었다. TDD와 관련된 자료를 찾아보니, 구현할 기능을 계획할 때 테스트 코드를 미리 작성해놓고, 이후에 새로운 규칙이 추가되거나 버그가 발견될 때마다 테스트를 추가하고, 실제 로직을 구현한 다음 리팩토링하는 식으로 진행하면 적절할 것 같다는 생각을 했다.
